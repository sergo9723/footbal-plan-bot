# Аудит №17 (v313) — широкий/узкий диапазон по сетке, разбор входа в GRAMUSDT, критичный баг ИИ-лимита

## 1. Широкий диапазон на 1-м ордере, узкий — после 2-го (по вашему запросу)

**Как было (v309-v312).** Breakeven-lock — «взвод» узкого диапазона выхода (порог пика 0.35%, выход у безубытка) — включался, как только исполнялся ПЕРВЫЙ ордер сетки, и не различал: усреднение уже завершено (оба из 2 ордеров исполнены) или нет. Именно так закрылась ваша сделка GRAMUSDT в 19:11 — пик +0.37%, откат до +0.18%, закрытие почти в ноль (Net −0.0012 USDT после комиссий), хотя обычный TP1/TP2 стоял гораздо дальше.

**Что изменил.** Теперь breakeven-lock проверяет `filled_orders_count` против `ORDER_COUNT` (у вас строго 2):

- Исполнен только 1-й ордер → breakeven-lock **выключен**, работает обычный широкий TP1/TP2 (как было до v309) — есть время на разворот и на то, чтобы цена дошла до тейка.
- Исполнены оба (1-й и 2-й) → усреднение завершено → breakeven-lock **включается**, как сейчас — узкий диапазон, ранняя фиксация у безубытка.

Код (`spot_bot_v313_fixed.py`, блок в `run()`):
```python
_bel_expected_orders = int(getattr(CFG, "ORDER_COUNT", 2))
_bel_filled_orders = int(getattr(self.pos, "filled_orders_count", 0))
_bel_full_grid = _bel_filled_orders >= _bel_expected_orders
if (
    _prices_sane
    and bool(getattr(CFG, "ENABLE_BE_LOCK_NO_TP1", True))
    and bool(getattr(CFG, "BE_LOCK_REQUIRE_FULL_GRID", True))
    and _bel_full_grid
    ...
):
```
Новый флаг `BE_LOCK_REQUIRE_FULL_GRID = True` — можно отключить (вернуть старое поведение) без правки кода.

**Честно про компромисс** (тот же, что обсуждали при добавлении breakeven-lock в v309, только теперь только для случая «1 ордер»): пока не исполнен 2-й ордер, между входом и TP1 защиты прибыли снова НЕТ — если цена подрастёт, не дойдёт до TP и развернётся, сделка полностью отдаст плюс, как было до v309. Вы сами описали это как правильное поведение для этого случая («вряд ли цена может развернуться» — это как раз про случай ПОСЛЕ 2-го ордера, поэтому там лок остаётся). Если увидите повторение «набрали плюс на 1-м ордере, не дошли до тейка, ушли в минус» — это будет ожидаемое, а не ошибочное поведение при новых настройках, дайте знать, если захотите добавить какой-то промежуточный узкий-но-не-такой-узкий уровень для этого случая тоже.

## 2. Почему бот зашёл в GRAMUSDT в 18:50:22 — разбор по логу (`___12.log`)

Короткий ответ: система не «ошиблась» технически — сработала цепочка из нескольких механизмов, каждый из которых по отдельности логичен, но вместе дали вход недалеко от вершины ложного пробоя. Разбор по времени:

| Время | Событие | Что означает |
|---|---|---|
| 18:20–18:30 | `GRAMUSDT: RSI=75>=72.0` / `RSI=77>=72.0` — отклонена сканером | Монета была перекуплена на пике пробоя — сканер её ПРАВИЛЬНО отсеивал |
| 18:37–18:45 | `vol_30m<0.8×ma` (объём затухает), `RSI velocity=15.3/14.6>12` (поздний вход) | Импульс явно затухал — тоже верно отсеивалась |
| 18:38:46 | `🔧 Авто-ослабление (максимальное): RSI_MAX 72→73` | Рынок весь день стоял почти без входов → мозг автоматически ослабляет фильтры (см. ниже) |
| **18:47:47** | `🟡 Scanner adaptive turnover fallback выбрал GRAMUSDT score=6.71` | Строгий сканер не нашёл НИ ОДНОЙ монеты во всём рынке → включился запасной, более мягкий алгоритм выбора (`adaptive turnover fallback`) |
| 18:48:04 | `PREBUY_GUARD_REJECT: last candle red (impulse dead)` | Более тонкий, минутный guard всё же поймал слабость и заблокировал первую попытку входа |
| 18:49:43 | Fallback снова выбрал GRAMUSDT (score=6.72) | RSI к этому моменту остыл (перепад с 75-77 до ~60), красная свеча прошла |
| **18:50:03** | `ENTRY_SCORE: entry=8.27/2.50 | main=base | ai=6.40 | pressure=1.33` | Композитный скор входа набрал 8.27 при пороге всего **2.50** |
| 18:50:19 | `[knowledge] Вход: GRAMUSDT ADX=32 RSI=60 T1 bot=base` | Вход состоялся |

**Три конкретные причины, почему порог оказался проходим:**

1. **Порог входа 2.50, а не выше.** `_entry_threshold()` берёт порог из `TRADE_ACTIVITY_MODE` — сейчас у вас режим **`active`**, порог = `ENTRY_THRESHOLD_ACTIVE = 2.50` (для сравнения: `balanced` = 3.5, `conservative` = 5.0). Это не баг, а ваша текущая настройка режима — но именно она даёт очень низкую планку, через которую легко проходит даже средний по качеству кандидат.
2. **Сигнал был "base", не SMC/fund.** `main=base` — вошли по базовому (самому простому, наименее избирательному) сигнальному боту, а не по более требовательным SMC/funding-ботам. AI-score был умеренный — `ai=6.40` из 15 (не сильный «купи», а нейтрально-положительный) — но так как база начисления идёт бонусами (`base=1.5`, `scanner_score`, `tradeability`, `ai×0.22`, `pullback_ok`...), даже умеренные подтверждения в сумме легко перекрыли низкий порог 2.50.
3. **Фильтр «не покупать у вершины» (`SCANNER_DIST_FROM_24H_HIGH_MIN_PCT = 1.5%`) сработал, но впритык.** По вашему скриншоту Bybit: 24ч максимум = 1.651, цена входа = 1.624 → расстояние от хая ≈ **1.63%**, то есть выше минимума в 1.5%, но лишь немного. Это тот самый фильтр, который должен был отсечь «покупку у сопротивления/на пике» — но 1.5% для монеты, только что улетевшей на ~5% за пару часов (1.579→1.651 по вашему графику), оказалось слишком тонким запасом, чтобы отличить «нормальный откат перед продолжением» от «мы всё ещё на хвосте ложного пробоя».

**Итог:** вход не был случайной ошибкой конкретной строчки кода — это результат совпадения (а) активного режима с низким порогом входа, (б) долгой рыночной «засухи», которая включила запасной алгоритм отбора монет, и (в) тонкого 1.5%-порога защиты от покупки у хая, который GRAM прошла впритык после того как первая волна перекупленности (RSI 75-77) уже спала. Каждый из трёх пунктов — сознательное проектное решение, а не баг, но комбинация именно на этой монете дала вход недалеко от локального пика.

**Не стал менять код здесь без вашего решения** — вы просили именно разобрать причину, а не сразу менять логику. Если хотите снизить вероятность повторения, есть два независимых, не конфликтующих между собой рычага (можно один, можно оба):
- поднять `SCANNER_DIST_FROM_24H_HIGH_MIN_PCT` с 1.5% до, скажем, 2.5–3% — конкретно для `base`-сигнала (SMC/fund можно не трогать, у них обычно более качественное подтверждение);
- при входе через `adaptive turnover fallback` (запасной алгоритм) требовать чуть более высокий порог входа, чем в обычном режиме — сейчас fallback пользуется тем же общим порогом 2.50.

Скажите, если делать один из этих вариантов — сделаю отдельной версией, чтобы можно было откатить, если станет реже находить сделки.

## 3. Найден и исправлен критичный баг — источник «слишком много запросов к ИИ» и спама «ошибка»

Это САМАЯ серьёзная находка в этом раунде, полностью объясняет вашу жалобу.

**Баг:** в основном цикле `run()` (крутится каждые `CHECK_DELAY=2` секунды) было условие:
```python
if _utc_h == 8:
    self.ai_advisor.ai_daily_forecast()
```
`_utc_h == 8` истинно **весь час**, с 08:00:00 до 08:59:59 UTC — а не только в момент наступления 8 утра. При цикле в 2 секунды это **до ~1800 вызовов `ai_daily_forecast()` за один час** вместо одного раза в день.

`ai_daily_forecast()` сама себя никак не ограничивает (в отличие от `check_nightly_report()`, у которой есть защита на 20 часов) — при каждом вызове запускается новый фоновый поток, который либо реально бьёт по Claude API (тратит вызов из дневного лимита `MAX_CALLS_PER_DAY=50`), либо, после исчерпания лимита (а при такой частоте это происходит за первые же минуты 8-го часа), шлёт в Telegram:
```
⚠️ Прогноз недоступен: дневной лимит 50 вызовов исчерпан
```
— и так может повторяться сотни раз подряд. Это именно то, что вы описали: «слишком много запросов, потратил весь лимит, потом каждый раз писал ошибку».

**Исправление:** добавлен дневной маркер (тот же приём, что уже используется для суточного PnL-отчёта):
```python
if _utc_h == 8 and getattr(self, '_ai_forecast_sent_date', '') != _utc_today:
    self._ai_forecast_sent_date = _utc_today
    self.ai_advisor.ai_daily_forecast()
```
Теперь прогноз уходит максимум 1 раз в день. На всякий случай тот же гейт поставлен и на утренний анализ рынка (`_utc_h==7`, сейчас это заглушка без реализации, но тот же класс бага сработал бы, если её когда-нибудь реализуют). Команда `/forecast` (по вашему запросу вручную) не трогалась — работает как раньше, без ограничений.

**Проверил остальные точки вызова ИИ** на тот же класс бага (вызов без гейта внутри цикла каждые 2с):
- `ai_score_symbol()` / `ai_analyze_entry()` (вызываются при сканировании) — имеют собственный кэш (TTL 600с/на ключ), избыточных вызовов не создают.
- `ai_correlation_signal()` — вызывается с собственным гейтом раз в 2 часа, к тому же сейчас это заглушка (без реального API-вызова).
- `check_mode_restore()`, `ai_market_regime()` — заглушки, реального вызова API нет.
- `review_blacklist()` — уже был на правильном гейте (раз в 7 дней).
- `check_nightly_report()` — уже был на правильном гейте (раз в 20 часов).

Баг был именно в одной точке (`ai_daily_forecast` на 08:00 UTC), но по масштабу (до 1800 лишних попыток в час) — самый серьёзный из всех точек вызова ИИ.
