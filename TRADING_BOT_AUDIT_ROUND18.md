# Аудит №18 (v314) — apply_mode() откатывал ослабление RSI_MAX, гонка потоков в мозге, тихий разбан монеты

Как договорились — проверил три конкретные области, которые раньше не разбирались отдельным глубоким проходом: переключение режимов (`apply_mode`), сохранение `bot_knowledge.json` при параллельных потоках, повторные попытки размещения ордеров. Нашёл и исправил **3 реальных бага**, один из них — с прямым подтверждением по вашему логу.

## 1. `apply_mode()` откатывал ослабление RSI_MAX при каждом переключении режима — подтверждено логом

Ещё в v226-1 (более старая правка) был закрыт похожий баг для `ADX_MIN`: раньше `apply_mode()` при смене режима откатывал любое ослабление фильтров, которое мозг сделал за время долгого простоя рынка. Тогда починили именно `ADX_MIN` — добавили правило «режим может только ужесточить порог, но не откатить ослабление мозга».

Но в этой же функции была ещё одна строка, чуть ниже, с комментарием «сброс после SNIPER» — она должна была сбрасывать RSI_MAX только при выходе ИЗ режима SNIPER. По факту она срабатывала **при любом вызове `apply_mode()` в НЕ-SNIPER режим** — включая обычный ежедневный полуночный сброс `apply_mode(SMART)` и авто-смену режима. Она безусловно перезаписывала `CFG.SCANNER_RSI_MAX` значением из профиля, стирая ту самую защиту от отката, которую несколькими строками выше эта же функция только что аккуратно применила.

**Подтверждение по вашему логу (`___8.log`):**
```
2026-07-04 22:39:57 | Авто-ослабление (максимальное): RSI_MAX 72→73   ← мозг ослабил после долгой засухи
2026-07-05 00:00:32 | apply_mode(SMART): ADX=33 (ослабление мозга сохранено)  ← плановый полуночный сброс режима
2026-07-05 00:51:27 | Авто-ослабление (ЭКСТРЕННЫЙ): RSI_MAX 72→73     ← ждали значение 73/74 (как оставили вечером),
                                                                          а видим снова 72→73 — откатилось!
```
То есть каждую полночь (и при любой авто-смене режима) RSI_MAX тихо откатывался к базовому значению профиля, и мозгу приходилось заново, с нуля, карабкаться по всей лестнице ослабления, теряя весь прогресс, накопленный за предыдущие часы простоя. Это удлиняло периоды «нет подходящих монет» больше, чем должно было быть.

**Исправление:** RSI_MAX теперь тоже уважает флаг `_relaxed` (ослабил ли мозг фильтры), как это уже было сделано для ADX_MIN — сохраняет более мягкое из двух значений вместо безусловного отката к профилю.

Отдельно проверил: ваш открытый вопрос-наблюдение («мозг поднял порог оборота посреди экстремальной засухи», всё ещё в списке задач без подтверждения) — это ДРУГОЕ поле конфига (`SCANNER_MIN_TURNOVER_SCAN`, меняется отдельной веткой авто-ослабления), не то, что чинит эта правка. `apply_mode()` действительно тоже сбрасывает поля оборота (`MIN_24H_TURNOVER_USDT`/`AUTO_TURNOVER_BASE`/`AUTO_TURNOVER_MIN`), но это другие переменные, и пока нет отдельного лога, подтверждающего именно такой же откат для них — оставляю тот вопрос как есть, без нового подтверждения.

## 2. Тихий разбан монеты при еженедельном ИИ-пересмотре blacklist (гонка данных)

`review_blacklist()` (в `ai_brain_advisor_v4.py`) раз в 7 дней просит ИИ пересмотреть чёрный список: читает `banned_coins.json`, отправляет список в Claude, ждёт ответ (запрос может занимать до ~25 секунд), и затем **записывает файл обратно, используя тот самый снимок данных, что был прочитан ДО запроса** — то есть до 25-секундной паузы.

Проблема: если за эти 25 секунд основной торговый поток успел добавить в тот же файл НОВЫЙ перманентный бан (аварийный выход по совершенно другой монете — это происходит в любой момент, независимо от ИИ-пересмотра) — при записи этот новый бан бесследно исчезал, потому что его не было в устаревшем снимке. Монету, которую бот только что забанил за реальный убыток, могло тихо «разбанить» побочным эффектом ежедневного/еженедельного ИИ-пересмотра, никак не связанным с этой конкретной монетой.

**Исправление:** перед записью файл теперь перечитывается заново, и из СВЕЖИХ данных убираются только те монеты, которые реально разрешил разбанить ИИ — всё остальное (включая баны, добавленные во время ожидания ответа от API) сохраняется.

## 3. Гонка потоков при сохранении `bot_knowledge.json`

`BotKnowledge._data` — общий объект в памяти, который читает и пишет главный торговый поток, но ТАКЖЕ мутируют три фоновых потока из `ai_brain_advisor_v4.py` (`_apply_loss_analysis`, `_run_nightly_report`, `_run_blacklist_review` — все три через `threading.Thread`), без единой блокировки. `_save()` сериализует `_data` в JSON (`json.dump`), итерируя по всем вложенным словарям/спискам — если в этот самый момент фоновый ИИ-поток добавляет запись (например, в `ai_learning_log`), Python может выбросить `RuntimeError: dictionary changed size during iteration` прямо посреди сохранения; ошибка тихо проглатывается (`except Exception` в `_save()`), сохранение просто пропускается без предупреждения.

Прямого лога с этой ошибкой у вас пока не было (значит на практике редко совпадает по времени), но это структурная проблема, не гипотеза — при более активной работе ИИ-советника (а мы в этом же раунде починили баг, из-за которого он раньше делал на порядки больше вызовов, см. v313) вероятность столкновения растёт.

**Исправление:** добавлена блокировка (`threading.RLock`) в `BotKnowledge`, `_save()` и все три фоновых мутатора в `ai_brain_advisor_v4.py` теперь используют её — сохранение и фоновые правки мозга больше не могут пересечься.
