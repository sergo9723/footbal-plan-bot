# Аудит №11 (v308) — почему «несколько минусов подряд»: не из-за очистки бан-листа, а куда серьёзнее

Разбор по логу `___11.log` (16:19–21:50) и Telegram-экспорту `result.json` за 08.07. Короткий ответ на ваш вопрос: **нет, дело не в том, что вы очистили `banned_coins.json`**. Причина глубже и серьёзнее.

## Что реально произошло — 3 сделки

| Монета | Время | Результат | Причина выхода |
|---|---|---|---|
| SLXUSDT | 16:31 | **+0.0582 USDT (ПРИБЫЛЬ)** | `time_stop` (взял прибыль по времени: profit=0.74%) |
| MMTUSDT | 16:55 | −0.1891 USDT (убыток) | `full_grid_early_stop` (сетка заполнена, убыток 1.20%) |
| LDOUSDT | 20:42 | −0.2111 USDT (убыток) | `full_grid_early_stop` (сетка заполнена, убыток 1.35%) |

Итого по этим трём: **+0.0582 − 0.1891 − 0.2111 = −0.342 USDT**. Ещё минус набежал из-за комиссий/просадки по нереализованным позициям в течение дня (equity day −0.9478 к 21:21) — но именно закрытых убыточных сделок всего две.

## Главная находка: бот банил НАВСЕГДА монету, которая ТОЛЬКО ЧТО ПРИНЕСЛА ПРИБЫЛЬ

Смотрите на лог сделки SLXUSDT дословно:

```
16:31:21  💰 [v291-4] Забираю прибыль: hold=1.2h profit=0.74%>=0.60%
16:31:22  🚫 [v119] SLXUSDT добавлен в permanent_emergency_blacklist (time_stop 1.18h loss=-0.74%)
16:31:29  🚫 [SLXUSDT] добавлен в blacklist (loss=-0.74% >= порог 0.3%)
16:31:31  🤝 [v217-trust] smc→loss pnl=-98.312% reason=time_stop 1.18h loss=-0.74%
16:31:31  ⚠️ [v216] smc WR<35% → weight=0.3 принудительно
16:31:31  [knowledge] Выход: SLXUSDT profit +0.0582 (time_stop 1.18h loss=-0.74%)
```

Строка 1 говорит «беру прибыль +0.74%». Строка 6 (правильная, финальная запись в базу знаний) подтверждает: **profit +0.0582 USDT**. Но между ними бот успел (а) забанить SLXUSDT навсегда и (б) записать сигнальному боту `smc` вымышленный убыток **-98.3%** и принудительно обрушить его вес доверия до 0.3 — **за прибыльную сделку**.

### Корень бага №1 — `abs()` в решении о бане

```python
if abs(loss_pct) >= _BAN_LOSS_THRESHOLD_PCT:
    self._add_to_permanent_emergency_blacklist(...)
```

`loss_pct` считается по формуле «вход минус текущая цена» — когда цена ВЫШЕ входа (то есть позиция в прибыли), `loss_pct` получается **отрицательным**. Обёртка в `abs()` превращает это обратно в положительное число и решение «банить» срабатывает **одинаково что для убытка, что для прибыли**, если движение цены превысило 0.3% в любую сторону. Комментарий в коде рядом прямо говорит про обратное намерение («НЕ банить монету при безубыточном выходе... банить только при реальном убытке») — но реализация делает противоположное для прибыльных сделок.

### Корень бага №2 — доверие к ботам-сигналам считало прибыль убытком

`BotKnowledge.log_trade_exit()` для решения «прибыль или убыток» для статистики доверия смотрит не на реальный исход сделки (который уже правильно посчитан), а **ищет подстроку в тексте причины выхода**. А текст причины и для настоящего убыточного `time_stop`, и для прибыльного «забираю прибыль по времени» — **одинаковый**: `"time_stop {часы}ч loss={X}%"`. Подстрока `"time_stop"` есть всегда → доверие резалось как за убыток, даже когда сделка была прибыльной.

### Заодно нашёл (третье, менее критичное) — «проценты» доверия к ботам были фиктивными

Число вроде `pnl=-98.312%` или встречавшиеся раньше в других отчётах `avg=-48.525%`, `pnl=-102.099%` — это не реальные проценты прибыли/убытка. Формула делила прибыль в долларах на несуществующий атрибут (`self._last_entry_cost`, который нигде в коде не устанавливается), из-за чего знаменатель всегда получался «прибыль ± копейка», и результат почти всегда выходил около ±100% независимо от реального размера сделки. Рядом в том же методе уже правильно посчитан процент (`pnl_pct` через настоящую цену входа) — переключил на него.

## Что исправлено (все три — в `BotKnowledge`/`run()`, файл `spot_bot_v308_fixed.py`)

1. Условие бана `abs(loss_pct) >= порог` → `loss_pct >= порог` — банит только при РЕАЛЬНОМ убытке, прибыльные `time_stop`-выходы больше не банят монету.
2. Из списка «эта причина = убыток» для доверия к ботам убраны `"time_stop"`/`"ext_time_stop"` — они теперь используют уже правильно посчитанный `outcome` вместо повторного (и в данном случае ошибочного) угадывания по тексту.
3. Проценты для доверия к ботам берутся из уже корректно посчитанного `pnl_pct`, а не из формулы с несуществующим атрибутом.

## При чём тут очистка бан-листа

Косвенно — да, отчасти: **MMTUSDT** (одна из двух реальных убыточных сделок) уже имел WR=0% по прошлым сделкам («AI score 18.7→14.7 (WR по монете 0% <40%)») — то есть это, похоже, была ранее заслуженно забаненная монета, которая после `/unban_all` получила второй шанс и снова потеряла деньги (-0.1891 USDT). Это ожидаемый риск разбана «плохих» (не только ошибочно забаненных) монет — я предупреждал об этом при добавлении `/unban_all`. **LDOUSDT** не была связана с очисткой бана — это обычная сделка, вошедшая во время рыночной просадки (много EMA-даунтренд сигналов в это время), сетка заполнилась и цена продолжила падать — обычный, штатно сработавший `full_grid_early_stop`.

Но **главная находка (баг с `abs()`)** — гораздо серьёзнее и не связана с разбаном вообще: она бьёт по КАЖДОЙ прибыльной сделке, закрытой через `time_stop`-механизм «забираю прибыль по времени», причём такие сделки, судя по всему, случаются регулярно. Это, вероятно, объясняет и часть давних наблюдений про постоянно низкое доверие к SMC-боту из прошлых раундов аудита.
