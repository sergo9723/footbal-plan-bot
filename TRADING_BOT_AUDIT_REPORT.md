# Полный аудит spot_bot_v296.py

Файл: `spot_bot_v296.py`, 18 239 строк, один класс `Engine` (172 метода) + класс-«мозг» `BotKnowledge` (~2000 строк) + `Config` (~800 строк). Биржа — Bybit Spot (pybit, unified_trading), торговля одной монетой в моменте, вход выбирается сканером рынка, далее сетка лимит-ордеров + AI-скоринг входа + тейк-профиты/стопы, обучающийся модуль пишет статистику по сделкам и подстраивает параметры.

Сам файл — это не «одна версия», а живая история из ~296 патчей (докстринг на 1800 строк вначале с русским changelog v1…v296). Это важно: это и есть один из корневых источников проблем — код правился точечно («заплатка на заплатку») без рефакторинга и без тестов, поэтому в нём накопились противоречащие друг другу проверки, дублирующаяся логика и в нескольких местах — банальные Python-баги (переменная используется до объявления), которые *годами* тихо проглатываются широким `except Exception` и никогда не всплывают как явная ошибка.

Аудит проводился 5 параллельными глубокими проходами по всем веткам логики (мозг/обучение, скан монет, вход по AI-скору, исполнение ордеров/риски, конфиг+инфраструктура). Ниже — сведённый отчёт.

## 0. СРОЧНО, ДО ЛЮБЫХ ДРУГИХ ДЕЙСТВИЙ: слитые ключи

**Критично.** В `Config` прямо в коде зашиты рабочие значения по умолчанию (используются, если не заданы переменные окружения):

- `API_KEY` / `API_SECRET` — Bybit API-ключ и секрет, **`TESTNET = False`, т.е. это реальный счёт** (строки 1830-1832).
- `TG_TOKEN` — токен Telegram-бота (строка 2033).
- `TG_ADMIN_ID` — ваш Telegram user_id (строка 2035).

Проверка на «плейсхолдер» в `main()` (~18226) ищет только строки вида `"ВСТАВЬ_КЛЮЧ_СЮДА"` и не видит, что тут уже стоят настоящие значения — то есть эта защита бесполезна против уже вписанных ключей.

Поскольку файл был загружен мне (третьей стороне) с этими значениями внутри — **немедленно, до продолжения работы с ботом**:
1. Зайти на Bybit → API Management → отозвать (revoke) этот API-ключ, создать новый.
2. Через @BotFather сделать `/revoke` токена и получить новый токен Telegram-бота.
3. Никогда больше не хранить ключи как значение по умолчанию в коде — только `os.environ["BYBIT_API_KEY"]` без fallback-строки, ключи — в `.env`/секретах хостинга, файл — в `.gitignore`.

Сами значения ключей я нигде не воспроизвожу — важен сам факт и то, что их надо считать скомпрометированными.

## 1. Корневые причины «плохих торгов» — по приоритету

### 1.2 Двойной счёт и рассинхрон весов скоринга

- `_ai_entry_score` (6816-6846) считает по сути **те же самые 6-7 сигналов** (тренд к EMA, пуллбэк, отскок, давление в стакане, зелёные свечи, размер последней свечи, «погоня» за ценой 5m/15m), которые `prebuy_entry_guard` уже отдельно штрафует/поощряет как самостоятельные бонусы. AI-скор добавляется поверх — то есть эти сигналы **фактически взвешены вдвое** относительно однократно учтённых факторов (тренд-контекст, пробой тренда, затухающий импульс и т.д.). Итоговый score скошен в пользу дублированных сигналов, а не отражает независимое подтверждение.
- В `_candidate_tradeability_score` (5834) диапазон «хорошего» пуллбэка захардкожен (`0.08–1.60%`) независимо от `CFG.MICRO_PULLBACK_MIN/MAX_PCT`, используемых чуть позже в реальном гейте — кандидат может получить бонус за пуллбэк, который тут же будет забракован как «слишком глубокий» адаптивным профилем.

### 1.3 Статистика на слишком малой выборке (мозг делает выводы из 2 сделок)

Несколько мест в `BotKnowledge` принимают решения, которые потом реально блокируют/двигают параметры, на основании **2 сделок**:
- `min_safe_adx` для монеты (строка 3900) — считается уже после 2 убыточных сделок с ADX<20 и потом жёстко скипает монету в сканере (12056-12058).
- «best_hours/worst_hours» — от 2 сделок в час (3911-3912).
- Штраф Tier-2 (строка 4930, порог `>=2`) — прямо противоречит соседнему блоку в этом же файле (строка 4313), который сам себя поправил на «минимум 5 сделок, 2 слишком мало для вывода» — то есть один и тот же вывод из одних и тех же данных делается дважды, разными порогами, и может сработать дважды за один вызов `apply_learning()`.
- `update_bot_trust` (3799-3803): при 3 сделках и WR<35% доверие к сигнальному боту жёстко режется до минимума — тоже очень маленькая выборка для решения, которое сохраняется на диск и влияет на все последующие сделки.

Небольшая выборка — это статистический шум, который «мозг» интерпретирует как закономерность и закрепляет надолго (учитывая, что откат «наверх» происходит гораздо медленнее/реже, чем ужесточение).

### 1.4 Часовой пояс UTC vs local в «шпаргалке по времени»

`log_trade_entry` пишет час сделки через `datetime.now().hour` (локальное время сервера, 3698-3710), а сканер при чтении `best_hours`/`worst_hours` явно берёт `datetime.utcnow().hour` (12542-12552, с явной пометкой «UTC» в логах). Если сервер не в UTC — бонус/штраф «золотого часа» применяется не в тот час, когда монета реально показывала хороший/плохой винрейт. Это прямо разрушает ключевую фичу из докстринга файла (v292 — «шпаргалка монет по времени»).

### 1.5 Разброс порогов «один и тот же индикатор — разные пороги в разных местах»

Проверка «EMA9 выше/ниже EMA21» на 1H встречается с разными допусками в разных местах: `0.999`, `0.9995`, `0.9998`, `1.0002`, `1.001` (строки ~11040, 11558/12558, 11594, 11623 и др.) — формально один и тот же тренд-фильтр, но с разной строгостью в зависимости от того, из какого места кода его вызвали. Комментарии показывают, что «унификация» этих порогов делалась несколько раз патчами, но не везде доведена до конца.

## 2. Скан монет — отдельно

**Как работает:** вся spot USDT-вселенная → грубый префильтр по тикеру (оборот) до ~120-200 кандидатов → на каждого кандидата **6-10 отдельных HTTP-запросов** (тикер, стакан, свечи 5m/15m/1h/4h, объём, памп за 2ч, возраст листинга, свечи для «шпаргалки») → ~15 последовательных жёстких фильтров → аддитивный score → топ-N дополнительно проверяется симуляцией входа.

**Проблемы, кроме уже перечисленных багов скоринга (п.1.1 №1-2, №7-8):**

- **Объём запросов к бирже.** При 120-200 кандидатах это **700-2000+ последовательных REST-запросов за один цикл скана**. Реальный риск упереться в rate-limit Bybit, а также то, что скан может занимать минуты — к моменту, когда бот выбрал «лучшую» монету и построил сетку, цена, по которой отбирался кандидат, уже устарела.
- **Перманентный чёрный список без амнистии.** `_add_to_permanent_emergency_blacklist` (10781-10930) навсегда (до ручного вмешательства) банит монету после одного аварийного выхода/стопа и сохраняет это в `banned_coins.json` — переживает рестарты. Поле `blocked_since` пишется, но нигде не читается для снятия бана. Один неудачный стоп (в том числе от шумного фитиля) навсегда сужает торгуемую вселенную.
- **Магическое число «наоборот».** Порог ADX для самого «отчаявшегося» уровня релаксации (после 50+ пустых сканов) — `22.0`, что **строже**, чем у менее отчаянных уровней (10-11), см. строку ~12891. Логика ослабления идёт «туда-сюда», что может держать бота в бесконечном цикле «streak≥50» без выхода.
- Дублирующийся, идентичный по смыслу блок сброса кулдауна символа встречается **дважды подряд** в одном месте (~12906-12911 и ~12922-12926) — мёртвый/избыточный код, источник путаницы при дальнейшей правке.
- Проверка «слишком мелкий тикшаг» заменена с честного запроса фильтров биржи на эвристику по цене (`price < 0.00005`, строка ~11912) ради экономии запросов — экономит API-лимит, но пропускает часть монет с грубым tick size, для которых и была придумана эта защита.

## 3. ИИ-«мозг» (BotKnowledge) — учится ли он реально?

**Да, это настоящий работающий контур обратной связи, не декорация.** `apply_learning()` (4225-5020) действительно пишет напрямую в глобальный `CFG` (ADX/RSI-пороги, SL/TP, шаг сетки, режим торговли) и вызывает `apply_mode()`/`apply_mode_with_brain()`; изменения сохраняются в `learned_cfg` и переживают рестарт. Я проверил (grep) — эти же значения реально читаются торговым движком в момент решений: `get_smart_tp`, `get_symbol_recovery_rate`, `is_good_hour_for_trading`, `get_tier_wr`, `symbol_stats["best_hours"/"worst_hours"/"min_safe_adx"]`, `get_market_regime`, `get_bot_weight` — то есть архитектурно всё подключено правильно, замкнутый цикл «сделка → лог → анализ → правка параметров → следующая сделка» существует.

**Но качество самого обучения хромает:**
- Баг с `changes_text` (п.1.1 №4) ломает как минимум один защитный триггер (медвежий рынок).
- Рассинхрон UTC/local (п.1.4) портит именно ту фичу, которую вы просили проверить в первую очередь («шпаргалка монет»).
- Решения принимаются на выборках 2-3 сделки (п.1.3) — это не обучение, а реакция на шум, причём с ассиметрией: ужесточение срабатывает быстро и на малых N, а откат — реже и по более строгим условиям.
- `update_bot_trust` (3799-3803) — есть жёсткий «мгновенный» оверрайд поверх более аккуратной логики с `n>=5`, который может обнулить доверие к сигнальному боту всего за 3 сделки.
- Список `trades` в `BotKnowledge` растёт **без ограничения** (все остальные списки в классе обрезаются: `[-50:]`, `[-100:]`, `[-200:]`), а `_save()` перезаписывает весь JSON-файл целиком почти на каждое действие — при долгой работе это линейно растущая стоимость каждой записи и растущий файл.
- Все 7 крупных секций `apply_learning` завёрнуты в собственные `try/except` — это правильно с точки зрения отказоустойчивости (одна упавшая секция не валит остальные), но именно поэтому баг п.1.1 №4 живёт необнаруженным до сих пор: ошибка тихо пишется в лог одной строкой и никто на неё не смотрит.
- Не найдено: обучения на ещё не закрытых сделках (data leakage), пересечения при итерации словарей, деления на ноль, одностороннего «трещоточного» дрейфа параметров только в одну сторону — по этим пунктам код в порядке.

**Вывод:** мозг спроектирован верно и реально влияет на будущие сделки, но 2 конкретных бага (п. 1.1 №4, п.1.4) и системная проблема «выводы из 2-3 сделок» снижают качество его решений и объясняют часть нестабильности результатов — обучение то помогает, то вносит шум, в зависимости от того, насколько «повезло» с первыми несколькими сделками по символу/часу/сигнальному боту.

## 4. Исполнение ордеров и риск-менеджмент

- **№5 из таблицы п.1.1 — самая опасная находка всего аудита**: усреднение в просадке в обход системы контроля экспозиции.
- **№6 из таблицы п.1.1**: «защитный выход» без логики стоп-лосса — архитектурная ловушка для будущих правок, риск отсутствия резервного выхода, если основной SL-код в `run()` не сработает.
- `call_with_retry` (2975-3062) ретраит **любое** стандартное исключение, включая таймауты сети, на вызовах `client.place_order` для BUY/SELL/аварийного IOC-SELL (строки ~8299, 9226, 13620-13629, 10875, 15650) — и нигде не передаётся `orderLinkId` (ключ идемпотентности Bybit). Если ордер по факту исполнился на бирже, а ответ потерялся по таймауту — ретрай **отправит дублирующий живой ордер**. Это системный риск дублирования сделок, не единичный баг.
- `total_exposure_usdt()` (9091-9096) при внутренней ошибке тихо возвращает `0.0` вместо отказа — в редком случае двойного сбоя это может «открыть» лимит на новую покупку при реально высокой занятой экспозиции (fail-open вместо fail-closed).
- `process_fills`: при отсутствии цены входа (entry_price=None) бот восстанавливает её по последним 5 BUY-филлам из истории ордеров (лимит 200 записей) — при длинной серии усреднений или после долгого времени жизни позиции это восстановление может взять не ту цену → неверный расчёт realized PnL → неверная работа дневного лимита убытка.
- Дневной «стоп по эквити» (`_daily_release_if_recovered`) в SOFT-варианте проверяет `realized_today`, а Telegram-сообщение при разблокировке говорит про восстановление «эквити» — не критично, но вводит оператора в заблуждение относительно реального условия снятия блокировки.
- После 2 подряд убыточных продаж бот сразу переключает монету (`do_switch`) и строит новую сетку почти на весь лимит экспозиции; полная пауза наступает только после 3 убытков подряд — то есть один порог «включает переключение» раньше, чем другой «включает паузу», и в связке с багом №5 (усреднение мимо лимитов) может ускорять серию мелких убытков на «дёрганном» рынке.
- Явных «голых» `except: pass` вокруг выставления/отмены ордеров, которые тихо теряют состояние без единой строки в лог, не найдено — почти все обработчики логируют (видны пометки `[FIX-v145-BARE-EXCEPT]` — это уже было исправлено в прошлых версиях).

## 5. Конфиг и инфраструктура

- **Ключи в коде — см. раздел 0, критично.**
- Потоки (threading) в порядке: `TelegramPolling` работает в отдельном потоке, но только кладёт разобранные команды в очередь под `threading.Lock`; вся мутация состояния `CFG`/`Engine` идёт синхронно в основном потоке через `handle_command()` после `TG.pop_all()` — гонок по торговому состоянию не найдено. Проверка `user_id != admin_id` отсекает команды от посторонних ещё до попадания в очередь — команда `/…` не может прийти от чужого пользователя.
- `eval`/`exec`/`pickle`/`subprocess`/`os.system` в файле не найдены — инъекций через Telegram-команды нет.
- Главный цикл `run()` целиком обёрнут в широкий `try/except`, с бэкоффом при сбоях API и корректной обработкой `KeyboardInterrupt` — учитывая историю патчей, это правильное защитное решение, а не недостаток.
- `START_SYMBOL = "SOLUSDT"` (1835) одновременно находится в `BLACKLIST_SYMBOLS` (2127, «слишком дорого для депозита $25») — если автосканер когда-либо падает на этот фолбэк, бот попытается торговать монету, которую сам же запрещает.
- `GRID_STEP_PERCENT=0.6` и `STOP_LOSS_PCT=0.8` находятся ровно на границе собственного правила бота «ATR_STOP_MIN >= GRID_STEP + 0.2%» без запаса и без runtime-проверки для не-ATR пути — любое ручное изменение шага сетки без синхронного изменения SL тихо нарушит это правило.
- Changelog документирует, что цепочка `DUMP_EXIT_PCT < STOP_LOSS_PCT < HARD_EXIT_LOSS_PCT` **ломалась и чинилась заново минимум 3 раза** (v122, v146, v283-285) — явный признак «затыкания дыр» без системной проверки инвариантов; сейчас (v296) значения (0.6/0.8/0.9) согласованы, но ничто в коде не мешает следующему ручному `/set` или правке профиля режима снова их рассогласовать за пределами двух явно защищённых Telegram-хендлеров.
